# 架构实战：数据转换服务

过去几年里我主导了很大一轮服务重构，其中有一些服务的设计比较不错，在这里分享一下。隐去一些业务相关的内容，但不会影响整个内部架构的实现。

本文要描述的服务，姑且称其为数据转换服务，其承担的职责主要包括几个部分：

- 老版本客户端协议数据接收
- 新版本客户端协议数据接收
- 数据分为多种类型，每种类型有不同的业务处理逻辑（这里的类型可能有些歧义，你可以理解为不同的 pb 结构）
- 不同数据类型有不同的数据计算逻辑
- 不同数据类型有不同的数据过滤校验
- 向后往多个下游服务进行数据发送

从功能上看，其对集群外部开放了多个协议的接口，对集群内部多个下游服务进行数据发送。这样的场景正合适六边形的服务架构。何为六边形服务架构？在《Microservices Patterns》书中有描述，简单概括就是其外部由多个协议适配器组成，核心为其关键的业务域逻辑。我们直接把书中的示例拿过来说明一下：

![image.png](/images/articles/architecture-practice-data-conversion-service-1.png)

这样的架构设计逻辑迥异于常规的MVC设计。在MVC设计中，常常分为控制层/接口层，逻辑层/领域层，存储层/底层服务，这样的分层结构有一种显示的层层向下的递进关系，原则上不允许跨层调用，在有多个上下游关系的服务中，力所不逮。而六边形架构中不再有明显的分层结构，我们可以将MVC中的逻辑层/领域层视为其逻辑核心，其外分别包括多种协议适配器：

![six_archtructure.png](/images/articles/architecture-practice-data-conversion-service-2.png)

大概是这个样子，该服务设计上并没有持久状态，也没有和数据库的交互，这极大的简化了我们的设计。

入向的适配器，对外提供的是http服务，当然各个适配器可以单独实现自己对外暴漏的接口语义，但要在适配器内部将协议转换为接口无关的中间数据结构，以转发给core domain进行数据处理。

出向的适配器也是相同的道理，将core domain处理完的内存数据转换为下游服务的协议格式将其转发出去。

下一步的设计是：如何来组织adapter 和 core domain的代码，以及如何划分线程结构。设计服务内部结构的时候，有个十二字箴言："**接口搭建框架，实现拓展细节**"。所以我们首先要做的是如何通过接口来表达我们的架构设计。通过分析该服务的业务逻辑，其功能可以抽象为一个数据处理流，每个数据的处理逻辑在入向 adapter 收到的一刻，即可确定下来，而不同的数据处理逻辑，包括：

- 协议解析，即 pb 数据的反序列化
- 协议的适配，老版本协议转换为新版本协议
- 不同类型数据的部分计算
- 不同类型数据的业务过滤
- 向下游服务的接口转发数据

可以将这些逻辑视为流水线，而服务的核心流程就是收到对应的数据，在这个流水线上将数据走一遍。这样的场景非常适合一种设计模式，责任链模式。

**责任链模式：使多个对象都有机会处理请求，从而避免请求的发送者和接收者之间的耦合关系。将这些对象连成一条链，并沿着这条链传递该请求，直到有一个对象处理它为止。**

为了后文行文方便，我们将责任链上的每个逻辑节点，称为一个处理器。首先为处理器定义一个接口：

```java
public interface IHandler<T> {
    bool handle(T data);
}
```

定义为模板是因为前文提到有多种数据类型，这样每种数据类型的处理逻辑就可以继承这个接口，特例化模板参数来实现自己的业务逻辑。为了使责任链的使用方更简单，我们可以再使用一个设计模式：组合模式。

**组合模式：将对象组合成树形结构以表示"部分 -整体"的层次结构。使得用户对单个对象和组合对象的使用具有一致性。**

实现一个特殊的handler, 其内部包含一个责任链表，在其handle中执行这个责任链表，使上层的调用者感觉不到责任链的存在，伪代码类似这样：

```java
public class IHandlerGroup implements IHandler<T> {
    private List<IHandler<T>> handlers;

    public bool handle(T data) {
        for (handler : handlers) {
            if (!handler.handle(data)) {
                return false;
            }
        }
        return true;
    }
}
```

通过这两个设计模式的组合，我们就将刚才说到的适配，计算，过滤，发送等等业务逻辑串联起来了。

但好像还不够完美，因为我们的业务逻辑涉及到多种数据类型，每种类型又有不同的计算逻辑，转换逻辑，过滤逻辑，零零总总会产生非常多的处理器，如何将这些处理器按照预期组合成我们期望的责任链，无疑是个复杂的过程。我们应该找个地方将这些逻辑集中起来，注意关键字，将复杂的创建过程封装起来，很明显的建造者模式。

**建造者模式：将一个复杂对象的构建与它的表示分离，使得同样的构建过程可以创建不同的表示。**

这里我们可以使用一些java和spring的特性来帮助我们简化构建过程。已知我们有一堆处理器，每个处理器适用于不同的数据类型。我们可以通过自定义一个注解，来标注处理器适用于哪种数据类型。之后通过spring的依赖注入过程收集到所有的处理器，再通过处理器上的注解将其分配到不同的责任链上。这样我们就解决了责任链的构建过程。

但做到这个地步，依然不够完美。这么多的处理器都在建造者中硬编码在一起，怎么控制哪个处理器在前，哪个处理器在后？如果不想某个处理器生效该怎么办？如果这样的简单诉求还需要修改代码才能实现，未免有些大动干戈。为了使代码的逻辑处理更为灵活，我们可以将责任链的构建参数提取到配置文件中，类似在yaml文件中定义：

A-data-type:

- handler-1

- handler-2

- handler-3

- handler-4

那就还剩下一个问题，配置文件中的名字从何处来？我们继续之前的注解方案，可以再添加一个注解，让处理器的实现者自定义处理器配置名称，这样一来，这个注解大概长这样

```java
public @interface HandlerAnnotation {
    String name(); // name in config
    DataType type(); // handler data type
}
```

每个处理器在继承IHandler接口之后，只需在类上添加上述的注解，就可以通过配置文件动态的生效到责任链表中，完全不会修改其他文件的任何一行代码，符合开闭原则，完美。

行文至此，我们解决了业务逻辑的串联问题。接下来处理第二个问题，线程结构该怎么定义？

首先，入向的adapter会启动自己的io线程来监听请求的到来，不论是从 kafka 这类 message queue 接收数据，还是开放http接口来接收数据，java的一般做法会在controller启动一系列的io线程来阻塞监听请求的到来，其底层大多是netty之类的nio，其内部有自己的线程池维护逻辑，没有对外暴漏出来，所以一般也不会在这些IO线程里原地执行业务逻辑。需要再另外开一个线程池来处理上述的业务逻辑。

这样就会有个问题：我们的多种数据处理责任链该怎么匹配线程？开多个线程池每个线程池处理一种责任链流程，这可能是首先进入脑海的想法。但这样一来，我们一是需要创建多个线程池，每个线程池配多大不好配置，二是超过cpu核心数量的线程对性能有害无益，三是我们无预知每种数据类型的数据量是否均衡，这更增加了线程数量的配置难度。

我们可以换一种思路来解决这个问题。在前文，我们已经将所有的处理逻辑否封装在了一个责任链里，再通过组合模式进行封装，所有的处理逻辑在controller层看来就是一个 handler，我们可以将这个handler和其要处理的接收到的数据，组合为一个，姑且称之为task的东西，这个task即包含要处理的原始数据，又包含要执行的处理过程，所以一个task的定义类似：

```java
public class Task<T> {
    private final T data; // process data
    private final IHandler<T> handler; // handler group

    public handle() {
        handler.handle(data);
    }
}
```

注意这里的T定义需要兼顾中间的计算数据，而非最原始的接收到的数据。只需将这个task投递到线程池的队列中，工作线程拿到task之后无脑的调用task的handle接口，这样一来我们就可以在一个线程池里处理所有的数据类型，妙哉。

在 controller 要处理的逻辑也非常轻便：

- 接收数据进行基本的校验
- 根据数据类型获取对应的 handler，组合为 task 投递到线程池中

以上是一个真实的服务内部架构的设计，我删除掉了一些业务相关的内容，但整体的设计思路没有受到影响。这个服务上线之后，只部署了四个实例就承担起来原来十二个旧服务的所有流量，称得上是功德圆满。

这个设计的初版印象，来自于 envoy。envoy 是一个高性能的L3，L4，L7层代理，在如日中天的service mesh技术中作为数据面的存在，其通过xDS协议动态的调整协议转换和转发过程，使用的设计方案和本文的思路基本类似。所以本文描述服务的设计，也可谓出身金贵！
